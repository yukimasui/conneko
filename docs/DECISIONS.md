# 設計判断の記録（ADR）

1 判断 1 エントリ。新しいものを下に足す。

## ADR-001 端子の案内は「選択中の機器だけ吹き出し」＋「ホバーで即ポップアップ」にする

- 日付: 2026-10-23
- 状況: リレーやセンサーを置いても、どの端子が何か分からない。端子の意味（note）は定義にあったが、
  端子の丸にマウスを乗せて少し待ったときのブラウザ標準のツールチップにしか出ず、ユーザーは存在に気づいていなかった
- 決定:
  - 選択中の機器だけ、端子の横（電線が出る向きの外側）に「印字 呼び名」の吹き出しを出す。上下の端子は縦書き
  - 端子にマウスを乗せたら、遅延なしで自前のポップアップ（意味・種別・受けられる電源・接続先）を出す
  - インスペクタの端子一覧を説明つきの表にする
- 採らなかった選択肢:
  - 全機器に常時出すトグル: 機器が多いと図が混み合う。印刷・SVG に載せる用途は今のところない
  - ホバーのポップアップだけ: 見に行かないと分からない点が変わらない
  - ブラウザ標準の title のまま: 出るまでに間があり、気づかれない（ユーザーから「ディレイ入らない」との要望）

## ADR-002 吹き出しの呼び名は定義の `hint` と自動の切り出しを併用する

- 日付: 2026-10-23
- 決定: 端子定義に任意の `hint`（10 文字まで。`validate.ts` の `HINT_MAX` で検査）を足す。
  書いていない端子は note の括弧より前 → 印字が「端子ID（説明）」の形なら括弧の中、の順で自動で作る（`src/devices/hint.ts`）
- 採らなかった選択肢:
  - 自動の切り出しだけ: リレーの note は「極 1 の COM（…）」と文章で、吹き出しには長い
  - 全機種に hint を必須にする: 333 機種あり、センサーなどは印字（「茶 +V（DC10〜30V）」）だけで足りる
- 補足: 意味の情報がない端子（印字が端子IDのままの端子台の番号など）は吹き出しを出さない。SVG に描いてある番号を重ねても情報が増えないため

## ADR-003 コネクタの「つなげる機器」の候補は、コネクタの種類から全機種を探して出す

- 日付: 2026-10-23
- 状況: IAI のロボシリンダーを置いても、どのコントローラーにつながるか選定が大変（ユーザーの要望）。
  互換性はコネクタの種類（`connector.kind` / `mates`）として定義に入っていた
- 決定（ユーザーと相談して決定）:
  - IAI 専用にせず、コネクタ全般を対象にする（PLC の MIL → 変換端子台、センサー → コネクタケーブルにも効く）
  - 引いた側のパラメータを 1 つ変えればつながる機種も、変更点つきで候補に出す。選ぶとそのパラメータも変える
  - 選ぶと、その場に置いてケーブルでつなぐ。同じ 2 台の間でほかにもつなげるコネクタ（モーター＋エンコーダー）はまとめてつなぐ。
    図面にある機器の空いているコネクタも候補に出す
  - 入口は「線を引いて離す」とインスペクタの「つなぐ機器を選ぶ…」の両方
- 採らなかった選択肢:
  - IAI 専用（適応コントローラー記号・ケーブル型式を候補に作り込む）: 仕組みは同じで、ほかのコネクタにも効く方が得
  - いまの設定でつながる機種だけ: RCON を使いたいとき先に設定を変える必要があり、選定が楽にならない
  - 置くだけでつながない: 線を引いた操作の意図とずれる

## ADR-004 コネクタのオス・メスは持たず、「同じ分類の機器は相手にしない」で候補を絞る

- 日付: 2026-10-23
- 状況: コネクタの種類は機器側とケーブル側（アクチュエーター側とコントローラー側）で同じ値のため、
  そのまま探すとアクチュエーターからほかのアクチュエーター、PLC ユニットからほかのユニットも候補に出た
- 決定: 引いた側と同じ `category` の機器は候補から除く。センサーとセンサー用コネクタケーブルは同じ `sensor` のため、
  ケーブルの機器定義に `cable: true` を書いて例外にする
- 採らなかった選択肢:
  - `ConnectorSpec` にオス・メス（または機器側・ケーブル側）を足す: 正確だが、全コネクタ（IAI だけで 30 種以上）に書き足す必要があり、
    つなげるかの判定（`connectorsMate`）にも影響する。分類で足りなくなったら見直す
- 既知の限界: 同じ分類どうしで本当につなぐ組み合わせ（ケーブル以外）があれば候補に出ない。手で線を引けばつなげる

## ADR-005 配線を文字で書く「配線言語」を、図面データへのコンパイラとして試験的に入れる

- 日付: 2026-11-14
- 状況: リレーの回路はラダーという言語になったが、盤の実配線（端子と端子を何番・何色・何 sq の電線でつなぐか）を人が書いて機械が調べる言語は
  確立していない（[調査](wiring-language-survey.md)。近いのは始まったばかりの JSON / YAML の形式だけ）。ユーザーから、配線を言語として書き、
  コンパイラのようにチェック・エラーを通せないかとの提案があった
- 決定:
  - 独自の構文（`.cnk`）を持つ言語を作り、図面データ（`Diagram`）へコンパイルする。電気的なチェックは新しく作らず、既存の配線チェックを
    コンパイルの第 2 段階として使い、指摘を書いた行へ戻す
  - 言語に書くのは接続だけ。配置（機器の位置・電線の曲がり・展開図）は書かず、アプリで反映するときに元の図面から引き継ぐ
  - 電線の種類（電線・ケーブル・チューブ）は書かせず、両端の端子の役割から決める。色・太さは `wire` ブロックでまとめて付ける
  - リンク（シート間の接続記号）は機器として宣言させず、電線の端に `<名前>` と書く
  - 図面 → 言語の逆変換も持つ（アプリで開いている図面をそのまま言語で見られる・書き換えられる）
- 採らなかった選択肢:
  - JSON / YAML のまま検査を足す: すでに図面 JSON がその役をしている。1 本の電線に 8 行かかり、人が書く・読む・差分を見るのに向かない
  - 既存の言語に乗る（WireViz、基板向けの SKiDL・atopile など）: ハーネスや基板が対象で、線番・sq・端末処理や AC/DC・保護の検査が合わない
  - 配置も言語に書く: 接続の意味と見た目が混ざる。機器の位置だけは `at x,y` で書けるようにした（元の図面なしで配置を保つため）
  - TypeScript / Python の内部 DSL: 単一 HTML のアプリの中でコンパイルできない。利用者にプログラミング言語の知識を求める
- 既知の限界: 新しく書いた機器は並べて置くだけ（配線に沿った自動配置はしない）。複数の電線にまたがる指摘は、いちばん後ろに書いた電線の行を指す
  （原因の行とは限らない。ほかの行は「関連」に出す）。回路の部品化・宣言した条件の検査はまだない（[wiring-language.md](wiring-language.md) の「これから」）
