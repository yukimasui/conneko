# 提案: 三菱電機 MELSEC の機器を表すために欲しい拡張

MELSEC iQ-R / iQ-F の機器定義（`src/devices/catalog/mitsubishi-*.ts`）を作る中で、既存の型・アプリでは表せなかった要素。
今回は型・アプリ本体は変更せず、機器定義側で次のように回避している。

## 1. 種類の違うコネクタをつなぐ変換ケーブル（FCN40 ↔ MIL40）

**現状**: iQ-R / Q / L の 32 点 I/O の 40 ピンコネクタは FCN 系で MIL とは嵌合しないため、kind `'FCN40'` にした。
アプリは同じ kind どうししかケーブルでつなげないので、RX41C4・RY41NT2P は既存の MIL 40P 変換端子台（`generic.mil-terminal-block.40p`）につなげない。
実際の盤では FCN40P−MIL40P 変換ケーブル（ミスミ PTHAS-F40-M40 など）で MIL 端子台に展開するのが一般的。

**提案**（どちらか）:

- `ConnectorSpec` に `mates?: string[]`（ケーブルでつなげる相手の kind）を追加し、FCN40 側に `mates: ['MIL40']` を書けるようにする。
  ピンID は既に変換ケーブルの結線（B20 ↔ MIL 1 …）にそろえてあるので、同じ番号どうしの導通のままでよい。
  ケーブル描画は既存の MIL ケーブルと同じでよい（PLC 側の端だけ FCN のプラグ形状にできればなお良い）。
- 汎用化するなら、ケーブル側に種類（`cableType: 'FCN40-MIL40'` など）と両端の kind・ピン対応表を持たせる。
  FCN40 → MIL20×2（東洋技研 KB40Y など）の分岐ケーブルにも対応できる。

## 2. ベースユニットへの装着と内部電源（DC5V）の配分

**現状**: iQ-R は電源ユニット・CPU・I/O をベースユニット（R35B など）に装着し、DC5V はベース経由で供給される。
Conneko の機器は独立したノードなので、ベースユニットも装着関係も表せない。CPU・I/O ユニットには電源端子がなく、
電源ユニットの DC5V 出力（R61P 6.5A など）と各ユニットの内部消費電流（R04CPU 0.67A、RX40C7 0.12A、RY10R2 0.45A …）の
収支もチェックできない。FX5 の増設ユニットも同様に、増設ケーブル経由で CPU の DC5V / DC24V（FX5U-32M は 5V 900mA、24V 400mA）を使う。

**提案**:

- 図面 JSON の機器に装着先を書けるようにする（例: `"mount": { "device": "BASE1", "slot": 2 }`、FX5 なら `"mount": { "device": "PLC1", "position": 1 }`）。
  エディタではベースユニットの上にユニットを並べて描き、装着順から先頭入出力番号を自動で求める。
- `DeviceDefinition` に内部電源の供給・消費を書く欄を追加（例: `busSupply: { '5V': 6.5 }`、`busLoad: { '5V': 0.12 }`）し、
  ベース単位で合計が供給能力を超えたら警告する。

## 3. 入出力番号（先頭番号）を端子名に反映

**現状**: 端子ID は X00〜X0F などユニット内の相対番号で、実際のデバイス番号（X20 など）は装着位置・割付けで決まる。
`label` は文字列固定なので、AI に渡す端子一覧に実際の番号を出せない（説明文で補足している）。

**提案**: `params` に先頭入出力番号（例: `ioHead`）を持たせ、`TerminalDef.label` / `PinDef.label` を
`svg` と同じくパラメータを受け取る関数にもできるようにする。2. の装着関係があれば自動で求められる。

## 4. AC と DC の両方を受けられる端子（リレー出力のコモン）

**現状**: リレー出力のコモン（RY10R2 の COM、FX5U-32MR/ES の COM0〜COM3）には AC240V 以下・DC30V 以下のどちらも入るが、
`AcceptSpec` は 1 つの system しか書けないため `signal` にした（電源の有無・電圧はチェックされない）。

**提案**: `accepts` に配列を許す（`accepts: [{ system: 'AC', minVoltage: 5, maxVoltage: 264 }, { system: 'DC', minVoltage: 5, maxVoltage: 30 }]`）。
いずれかを満たせば OK とする。

## 5. 出力の ON/OFF とコモンあたりの電流

**現状**: 既存の「接点は閉とみなす」に合わせ、出力端子とコモンを `links` でつないで出力 ON の状態として扱っている。
これで負荷の電圧・極性はチェックできるが、次は表せない。

- 1 コモンあたりの合計電流（RY10R2 8A/コモン、FX5U リレー 8A/4 点、トランジスタ 0.8A/4 点 など）と 1 点あたりの定格（2A、0.5A）。
- 出力ごとの負荷の定格電流がわかれば合計と比較できる。

**提案**: `InternalLink` に `ratedCurrent`（1 点の定格）を、`DeviceDefinition` に `commonLimits: { terminal: 'COM', current: 8 }` のような
コモンごとの上限を書けるようにし、つながっている負荷の `loadCurrent` の合計と比較する。
あわせて `links` に `kind: 'contact' | 'output'` を持たせられると、AI 用の説明やチェックで「常時導通」と区別できる。

## 6. 入力のシンク/ソースとセンサーの出力形式

**現状**: FX5U の S/S や iQ-R 入力ユニットの COM は `+` / `−` どちらも受ける `input` にしたので、
「S/S を 24V につないだ（シンク入力）のに PNP（ソース出力）センサーをつないだ」のような組み合わせの誤りは検出できない。

**提案**: センサー機器（NPN/PNP）を追加する際に、入力コモンの極性とセンサーの出力形式の組み合わせを検査するルールを検討する。
