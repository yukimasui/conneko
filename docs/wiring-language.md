# 配線言語（.cnk）— 試験的

機器と電線を文字で書き、コンパイルして図面データ（[conneko-diagram](data-format.md)）にする言語。
書いたものはコンパイラが調べ、誤りを「ファイル:行:桁」つきで返す。v0.6.47 で試験的に入れた。

```
// 三相モーターの直入れ始動（自己保持回路）
PS1  = generic.power-source.3p200v
ELB1 = mitsubishi.nv32-sv.3p(ratedCurrent=15)
CP1  = mitsubishi.cp30-ba.2p(ratedCurrent=3)
MC1  = mitsubishi.s-t10.ac200v
THR1 = mitsubishi.th-t18(heater=3.6)
M1   = generic.motor.3p(ratedCurrent=3.6) "コンベア駆動"
PB1  = fuji.ar22f0r-11(color=R) "停止"
PB2  = fuji.ar22f0r-11(color=G) "運転"

wire KIV 2sq black {
  [R, S, T]:    PS1.[R, S, T]           -- ELB1.[1, 3, 5]
  [R1, S1, T1]: ELB1.[2, 4, 6]          -- MC1.[1/L1, 3/L2, 5/L3]
  [U1, V1, W1]: MC1.[2/T1, 4/T2, 6/T3]  -- THR1.[1/L1, 3/L2, 5/L3]
  [U, V, W]:    THR1.[2/T1, 4/T2, 6/T3] -- M1.[U, V, W]
  [R1, S1]:     ELB1.[2, 4]             -- CP1.[1, 3]
}
E: PS1.PE -- M1.E  green 2sq

wire KIV 1.25sq red {
  R2: CP1.2   -- PB1.1
  1:  PB1.2   -- PB2.3 -- MC1.13
  2:  PB2.4   -- MC1.14 -- THR1.95
  3:  THR1.96 -- MC1.A1
  S2: CP1.4   -- MC1.A2
}
```

見本は [`examples/`](../examples) にある（`motor-starter.cnk`、アプリのサンプル図面と同じ `conveyor.cnk`、誤りの見本 `errors.cnk`・`short-circuit.cnk`）。

## なぜ言語にするのか

リレーのシーケンス回路はラダーという言語になり、書いたものを機械が調べられるようになった。一方、盤の実配線（どの端子とどの端子を、何番の何色・何 sq の電線でつなぐか）は、
人が作業する前提のまま図面と表で受け渡され、人が書ける言語とコンパイラは確立していない（[調査](wiring-language-survey.md)）。

Conneko には、図面データを調べる配線チェック（短絡・電圧の不一致・電線の太さ・安全回路など）がすでにある。配線言語は、その入口を「絵を描く」から「文字で書く」に広げたものにあたる。

- **コンパイラのように誤りを返す**: 機器種別・端子 ID・パラメータの書き間違いは名前の解決で、短絡や太さの不足は電気的なチェックで見つけ、どれも書いた行を指す。
- **生成AIに渡しやすい**: 同じ図面が JSON の約 1/8 の大きさになる（サンプル図面で JSON 45KB に対し 5.3KB）。AI が書いた結果の誤りは、行番号つきの指摘をそのまま貼って直させられる。
- **差分が読める**: 1 行 = 1 つの宣言・1 つの接続なので、Git の差分やレビューで「どの電線を変えたか」が分かる。
- **配置と意味を分ける**: 言語には接続だけを書く。機器の位置・電線の曲がりは画面で決める（ラダーが接点の座標を書かないのと同じ）。

## 使い方

### アプリ

上のバーの「配線言語」で、いまの図面を言語にしたソースが開く。書き換えるとその場でコンパイルし、右に指摘が出る（クリックするとその行を選ぶ）。
「図面に反映」で図面を入れ替える（Ctrl+Z で戻せる）。構文・名前のエラーがある間は反映できない。電気的な指摘は、画面で描いたときと同じく残っていても反映できる。

反映するとき、言語に書かない配置は元の図面から引き継ぐ。

| 引き継ぐもの | 見分け方 |
|---|---|
| 機器の位置 | 同じ機器名 |
| リンクの機器名・位置・向き | 同じシート・同じ名前で、つないだ相手の端子が同じ |
| 電線の ID・曲がり・経路・出す向き | 両端の端子が同じ |
| 展開図の配置、工程（`settings.operation`）、チューブの巻（`tubeRoll`） | 図面全体 |

新しく書いた機器は、そのシートの機器の下に並べて置く。

### コマンドライン

```bash
npm run cnk -- check examples/motor-starter.cnk     # コンパイルとチェック。エラーがあれば終了コード 1（--strict で警告も 1）
npm run cnk -- build examples/conveyor.cnk out.json # 図面 JSON にする（アプリの「開く」で読める）
npm run cnk -- print 図面.json                      # 図面 JSON を配線言語にする（--positions で機器の位置も書く）
npm run cnk -- devices 漏電                         # 機器カタログから機器種別を探す
npm run cnk -- terminals mitsubishi.s-t10.ac200v    # 機器の端子 ID とパラメータを見る
```

指摘の表示:

```
examples/errors.cnk:10:31: error[unknown-terminal]: M1（3φ 200V 4P 全閉外扇形）に端子 X はありません（もしかして: E、U、V）。端子: U、V、W、E
   10 |   ELB1.[2, 4, 6] -- M1.[U, V, X]
      |                               ^

examples/short-circuit.cnk:23:7: error[mixed-system]: 混触: 交流(AC)と直流(DC)の電源がつながっています
   23 |   T1: ELB1.6 -- PL1.X1
      |       ^^^^^^^^^^^^^^^^
      = 関連: W3（10 行目）
```

## 文法

改行が文の区切り。空白は自由に入れてよい（そろえて書ける）。コメントは `//` と `#`（どちらも行頭か空白の後から行末まで）。

### 機器

```
名前 = 機器種別(パラメータ=値, …) "コメント"
```

```
ELB1 = mitsubishi.nv32-sv.3p(ratedCurrent=20)
M1   = generic.motor.3p "コンベア駆動"
```

- 名前は図面内で一意。空白と `.` は使えない。
- 機器種別とパラメータは機器カタログのもの（`npm run cnk -- devices` / `terminals` で調べる。図面 JSON の `type` / `params` と同じ）。
- 後ろに `at x,y`（キャンバス上の位置）を書ける。書かなければ自動で並べる。

装着するユニット（PLC の増設ユニット、マニホールドの連）は、親のブロックの中に書く。書いた順に位置 1, 2, … になる。

```
PLC1 = keyence.kv-8000.cpu {
  IN1  = keyence.kv-c32xc.input
  OUT1 = keyence.kv-c32tc.output
  OUT2 = keyence.kv-c32tc.output slot 5   // 位置を飛ばす
}
IN9 = keyence.kv-c32xc.input on PLC1 slot 6  // ブロックの外に書く形
```

### 電線

```
線番: 端子 -- 端子  属性…
```

- 端子は `機器名.端子ID`（例: `MC1.1/L1`、`PSU1.+V1`、`IN1.CN1#1`、`CY1.SW1.BN`）。最初の `.` までが機器名。
- `--` の前後は空白で区切る（端子 ID に `-` が入るため）。
- 線番は省ける。空白などを含む線番・端子 ID は `"…"` で囲む（`"A 1": AD1."IN COM" -- X.1`）。
- 電線に向きはない。

属性は順不同で、形で見分ける。

| 書き方 | 意味 |
|---|---|
| `black`、`赤` | 色（`src/data/wires.ts` の ID か日本語名） |
| `3.5sq` | 太さ |
| `KIV`、`VCT` | 電線の種類 |
| `ferrule`、`ring`、`fork`、`bare` | 端末処理（両端）。片方だけは `from=…` / `to=…` |
| `6mm` | チューブの外径 |
| `cable=…` | 変換ケーブルの種類（`src/data/cables.ts` の ID） |
| `no=…` | 線番（`wire` ブロックでまとめて付けるとき） |

書かない属性は既定（KIV 2sq 黒）になる。

**電線の種類は書かない**。コネクタどうしをつなげばケーブル、エアのポートどうしをつなげばチューブになる（両端の端子の役割から決まる）。

```
CBL1: IN1.CN1 -- TB1.CN         // MIL ケーブル
AIR1.OUT -- FR1.IN  8mm         // チューブ
```

### 並んだ電線

`機器名.[端子, 端子, …]` は同じ機器の端子の並び。`--` の両側が同じ本数なら順につなぎ、線番も `[…]:` で順に付ける。

```
[R, S, T]: PS1.[R, S, T] -- ELB1.[1, 3, 5]     // 3 本
```

片方が 1 本なら、その端子からすべてへつなぐ。別々の機器の端子は `[端子, 端子]` で並べる。`[1..8]` は 1 から 8 までの番号。

```
PSU1.+V1 -- [PL1.X1, PH1.BN]                   // 2 本（どちらも PSU1.+V1 から）
PSU1.-V1 -- TB1.[1..8]                         // 8 本
```

本数が合わない（3 本と 2 本など）のはエラー。

### 渡り配線

`--` を続けると、端子から端子へ順に続く電線になる。線番はすべての電線に付く。行を分けてもよい（`--` の前後の改行は続きとして読む）。

```
P24: PSU1.+V1 -- PL1.X1 -- PL2.X1              // PSU1→PL1、PL1→PL2 の 2 本
N24: PSU1.-V1
  -- PL1.X2
  -- PL2.X2
```

### 電線の既定（wire ブロック）

ブロックの中の電線に、同じ属性を付ける。入れ子にでき、内側と文に書いた属性が優先する。

```
wire KIV 0.75sq blue {
  P24: PSU1.+V1 -- PL1.X1
  wire red {
    PB1.3 -- PL1.X2  1.25sq
  }
}
```

### リンクとシート

`<名前>` はリンク（同じ名前どうしがつながる記号。別のシートや離れた場所へ渡す）。電線の端に書くと、相手の端子のそばにリンクが置かれる。
線番を書かなければ、リンクの名前が線番になる（線番を付けないときは `"":` と書く）。

```
sheet "DC24V電源" {
  PSU1 = generic.psu.dc24v
  PSU1.+V1 -- <P24>  blue 0.75sq
}
sheet "入出力機器" {
  PH1 = keyence.pz-g41
  <P24> -- PH1.BN    blue 0.75sq
}
```

- `sheet ID "名前" { … }`。ID は省ける（順に S1, S2, …）。同じシートを何度開いてもよい。
- リンクの種類は相手で決まる（LAN の通信ポートならネットワークリンク、エアのポートならエアのリンク）。
- リンクを書かずに別のシートの端子どうしをつないでもよい。コンパイル時にリンクの組に置き換わる。

### 端子のコメント・図面の設定

```
comment IN1.CN1#1 "PH1 ワーク検出"
title "コンベア制御盤"
author "…"
revision "A"
requiredPL d
```

## コンパイラが調べること

2 段階で調べる。第 1 段階にエラーがあると、第 2 段階は行わない。

### 1. 構文と名前の解決

| コード | 内容 |
|---|---|
| `syntax` | 構文の誤り。その行を読み飛ばして続けるので、複数の誤りを一度に出す |
| `unknown-device` | カタログにない機器種別、宣言していない機器（近い名前を示す） |
| `unknown-terminal` | その機器にない端子 ID（近い名前と、端子の一覧を示す） |
| `duplicate-device`、`invalid-name` | 機器名の重複、使えない文字 |
| `invalid-param` | 選択肢にないパラメータの値（選べる値を示す） |
| `invalid-attr` | 読めない電線の属性 |
| `width-mismatch` | 並んだ電線・線番の本数の違い |
| `self-wire` | 同じ端子どうしの接続 |
| `unknown-param`、`wire-size`、`duplicate-wire`（警告） | 定義にないパラメータ、その種類にない太さ、同じ 2 つの端子を結ぶ電線の重なり |

### 2. 電気的なチェック

できた図面データに、アプリと同じ配線チェック（`src/check`）をかける。指摘は、その電線を書いた行（機器についての指摘は機器を宣言した行）に戻す。
複数の電線にまたがる指摘（混触など）は、いちばん後ろに書いた電線の行を指し、ほかは「関連」に出す。

未接続、短絡・地絡・混触、電圧・極性の不一致、保護機器なし、電線の太さ不足、接点・出力の定格、NPN/PNP とコモン、安全回路、PLC の内部電源、エアの圧力など
（[features.md](features.md) の「配線チェック」）。コードは配線チェックのルール名（`wire-too-thin`、`mixed-system` など）。

## 図面 → 配線言語

`printDiagram`（`npm run cnk -- print`、アプリの「配線言語」）は、図面をこう書く。

- 機器はシートごと。装着したユニットは親のブロックの中。
- 電線は「種類・太さ・色」ごとに `wire` ブロックにまとめる。同じ 2 台の間に並ぶ電線は `A.[…] -- B.[…]`、同じ線番で続く電線は渡り配線にまとめる。
- リンクは機器として宣言せず、電線の端に `<名前>` と書く。
- 同じ端子と同じリンクを結ぶ、属性も同じ電線の重なり（シートをまたぐ電線をリンクに置き換えるとできる）は 1 本にまとめる。

言語にしたソースをコンパイルすると、機器・接続・チェック結果が元の図面と同じになる（`src/lang/lang.test.ts` の「図面 → 配線言語 → 図面」）。

## 書けないもの（いまのところ）

- 配置: 電線の曲がり・経路、リンクの向き、展開図の配置（元の図面から引き継ぐ）。機器の位置は `at` で書ける。
- 図面の設定のうち工程（`operation`）とチューブの巻（`tubeRoll`）。
- 回路の部品化（下の「これから」）。

## これから（案）

実装していない。使ってみて必要なものから決める。

1. **生成AIとのやりとりを配線言語で**: 「AI用にコピー」を配線言語で出し、AI が返したソースをコンパイルして、指摘をそのまま返せるようにする。
2. **回路の部品化**: 「直入れ始動」「正逆転」「PLC 入力 1 点」のような決まった回路に名前を付け、機器名と定格を変えて呼び出す
   （`starter(M1, 3.6A)` のような形）。ラダーの FB にあたる。
3. **回路の区分**: `wire` ブロックに「主回路」「DC24V 制御」のような区分を持たせ、色・太さの社内標準を 1 か所で決める。
4. **宣言した条件の検査**: 「MC1 と MC2 は同時に入らない」「非常停止で MC1 が落ちる」のような条件を書き、接点の状態から確かめる。
5. **配線作業への展開**: 線番順の配線手順（どの電線を何 mm で切り、どの端末処理で、どこからどこへ）を言語から出す。電線の自動加工機・配線支援への入口になる。

## 実装

| ファイル | 役割 |
|---|---|
| `src/lang/lexer.ts` | 字句解析（位置つき） |
| `src/lang/parser.ts`、`ast.ts` | 構文解析・構文木 |
| `src/lang/compile.ts` | 名前の解決と図面データの組み立て（ソースの位置との対応を持つ） |
| `src/lang/check.ts` | コンパイル + 配線チェック → 位置つきの診断、コンパイラ風の表示 |
| `src/lang/print.ts` | 図面データ → 配線言語 |
| `src/lang/merge.ts` | 元の図面からの配置の引き継ぎ |
| `src/editor/LangDialog.tsx` | アプリのエディタ |
| `scripts/cnk.ts` | コマンドライン |

機器カタログは引数（`lookup` / `defs`）で渡す（アプリは `registry.ts`、コマンドラインは `src/devices/catalog/` を直接読む）。
